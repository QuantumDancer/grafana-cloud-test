# Browser loop's cart, checkout and lens-care steps have never run

Status: ready-for-agent

`load/browser/shop-browser.js` uses Playwright-only `:has-text()` pseudo-selectors, which
k6/browser does not implement — it forwards them straight to `document.querySelectorAll`,
which throws. Verified in the live pod's logs:

    level=warning msg="add to cart failed: clicking on \"button:has-text(\\\"Add to cart\\\")\":
      SyntaxError: Failed to execute 'querySelectorAll' on 'Document':
      'button:has-text(\"Add to cart\")'"
    level=warning msg="checkout failed: clicking on \"button:has-text(\\\"Proceed to checkout\\\")\": SyntaxError: …"

Affected lines: **83, 85, 91, 93, 108**.

This matters more than a failing selector usually would, because the browser loop is our
**sole Faro telemetry source besides real users** (per issue 08). `safeStep` swallows each
failure into a failed check and the loop continues, so the pod looks healthy and keeps
reporting — but it has only ever exercised catalog and product-detail pages. Cart,
checkout and the planted `/lens-care` error route have never been driven.

Two things follow that were previously mysterious:

- Frontend O11y session data is narrower than it appears — no checkout funnel, and no
  automatically-generated frontend exceptions.
- The `checks: ['rate>0.5']` threshold at line 46 is crossed every cycle
  (`level=error msg="thresholds on metrics 'checks' have been crossed"`), which had been
  read as noise.

## Fix

Replace the five `:has-text()` selectors with k6/browser-supported locators. Prefer
role-based locators over structural CSS so the script does not re-break on markup changes;
the image is `grafana/k6:2.1.0-with-browser` (`charts/shop/values.yaml:206`), which has the
`getByRole` family.

All five targets are plain elements with static text, so the mapping is direct — markup
confirmed in the frontend source rather than guessed:

| line | current | element | source |
|---|---|---|---|
| 83 | `button:has-text("Add to cart")` | `<button>` | `routes/ProductDetailPage.tsx:66` |
| 85 | `a:has-text("View cart")` | `<Link>` → `<a>` | `routes/ProductDetailPage.tsx:71` |
| 91 | `button:has-text("Proceed to checkout")` | `<button>` | `routes/CartPage.tsx:56` |
| 93 | `button:has-text("Place order")` | `<button>` | `routes/CheckoutPage.tsx:88` |
| 108 | `button:has-text("Load detailed coating chart")` | `<button>` | `routes/LensCareGuidePage.tsx:43` |

Two markup details that will bite otherwise:

- **"View cart" only exists after a successful add** — it lives inside the "Added to cart."
  confirmation (`ProductDetailPage.tsx:71`), so line 85 must wait for it to appear rather
  than assume it is present once line 83's click returns.
- **The "Place order" button renames itself to `Placing order…` while submitting**
  (`CheckoutPage.tsx:88`). Fine for the click at line 93, but nothing afterwards may match
  on the original name.

The frontend's own tests already drive this markup by role — e.g.
`getByRole('button', { name: 'Place order' })` at `routes/CheckoutPage.test.tsx:55` — so
the accessible names are known-good and worth mirroring.

## Non-goal: leave `safeStep` alone

`safeStep`'s swallow-and-continue behaviour is what let five broken selectors run unnoticed
for a whole session, and a step that fails on *every* iteration is a defect rather than a
flake — so there is a real argument for failing the run instead of warning. That is a
design decision about what the loop is for, not part of this fix, and changing it here
would conflate "the selectors were wrong" with "the loop should be stricter". Deliberately
deferred; raise it separately if the appetite is there.

Done: cart, checkout and lens-care steps complete in the loop; the `checks` threshold
stops being crossed; Faro shows checkout-funnel sessions and the planted frontend error
arriving without manual browsing.
