# Kubernetes Monitoring cost tab is empty — cost collection was never deployed

Status: resolved

The Cost tab shows empty panels or $0 because nothing has ever collected cost metrics.
This is not a data-latency or short-runtime problem: **zero** series exist, not sparse ones.

## Evidence

- `infra/40-platform/k8s-monitoring.tf:19-169` — the `values` block has no `costMetrics`
  key at all. `telemetryServices` (`:88-95`) declares only `kube-state-metrics` and
  `node-exporter`; no `opencost`. Chart 4.3.2 defaults both `costMetrics.enabled` and
  `telemetryServices.opencost.deploy` to `false`.
- Repo-wide grep for `cost|opencost|billing|cur` over `locals.tf`, `variables.tf`,
  `terraform.auto.tfvars` → 0 matches.
- Live cluster: no opencost/kubecost/kepler pod in any namespace; the rendered
  `k8s-monitoring-alloy-metrics` config contains 0 cost-related components.
- Grafana Cloud: a query for all 25 metrics in the chart's own `opencost.yaml`
  allow-list returns empty, while control queries on the same datasource return
  `kube_pod_info` = 21 series, `node_cpu_seconds_total` = 190, `up` = 17.

An AWS CUR/billing integration is **not** required: OpenCost reads
`node.spec.providerID` and applies AWS public on-demand pricing unaided. CUR only
improves accuracy for spot/RI/negotiated rates.

## Fix

In `infra/40-platform/k8s-monitoring.tf`, add to the `values` yamlencode:

1. `costMetrics = { enabled = true, collector = "alloy-metrics" }`
2. A `telemetryServices.opencost` entry: `deploy = true`,
   `metricsSource = "grafanaCloudPrometheus"`, `opencost.exporter.defaultClusterId`
   equal to `cluster.name` (`spyglass`), plus `opencost.prometheus.external.url` and
   basic-auth credentials.

## Prerequisite — probe first, then take one of two branches

OpenCost must **query** a Prometheus-compatible endpoint, not merely remote-write to
one. The 30-grafana-cloud remote state exposes no query URL — its outputs are
`destinations_token, faro_*, k6_project_id, loki_url, loki_username, otlp_url,
otlp_username, prometheus_remote_write_url, prometheus_username, stack_id, tempo_*`.

The URL itself is derivable inside `locals.tf` by trimming `/push` from the
remote-write URL (`…/api/prom/push` → `…/api/prom`), which keeps that part of the
change in 40-platform. **Unverified**: whether `destinations_token` carries Prometheus
*read* scope. If it is write-only, 30-grafana-cloud must mint a read-scoped token
first, making this a two-component change.

Resolve this by probing rather than by reading policy definitions — one authenticated
`GET …/api/prom/api/v1/query?query=up` against the derived read URL with
`prometheus_username` + `destinations_token` settles it. Then branch:

- **Read-scoped (200)** — the whole change stays in 40-platform: derive the query URL in
  `locals.tf` and wire it into the `opencost.prometheus.external` block.
- **Write-only (401/403)** — mint a read-scoped access policy + token in
  30-grafana-cloud, expose it as an output, and consume it from 40-platform. Do the
  30-grafana-cloud half first; it is a prerequisite, not a parallel change.

Report which branch was taken, since it changes whether 30-grafana-cloud was touched.

Done: the Cost tab populates with non-zero values, and `opencost_*` /
`node_total_hourly_cost` series are present in Grafana Cloud.

2026-08-07 resolved. **Branch taken: write-only** — the probe this ticket prescribed
returned `401 invalid scope requested`, matching `destinations.tf:17`
(`metrics:write, logs:write, traces:write`, no read). A control probe with a corrupted
token returned a *different* body (`invalid authentication credentials`), so the token was
valid and only the scope was missing. **30-grafana-cloud was therefore touched.**

The ticket's write-only branch as written ("mint a read-scoped token, expose it, consume
it from 40-platform") turns out not to install: the chart validates that
`telemetryServices.opencost.opencost.prometheus.existingSecretName` is the metrics
destination's *own* generated Secret, which forces OpenCost onto the same
`destinations_token` Alloy pushes with. A separately minted token is only reachable via
`metricsSource: custom` plus a hand-rolled Secret in 40-platform. Maintainer chose the
cheaper option for a disposable stack: **widen the existing policy with `metrics:read`**
(one line in `destinations.tf`). Verified from provider source and live that this is an
in-place update — the token is not rotated, so 40-platform needed no credential re-apply.
The trade is that the shared push token can now also read every metric in the stack.

Two other corrections to the fix as specified: `existingSecretName` was missing from the
`values` list and is mandatory; and no `/push` string-trimming was needed, because
`data.grafana_cloud_stack.this.prometheus_remote_endpoint` already *is* the `/api/prom`
query URL — 30-grafana-cloud just gained a `prometheus_query_url` output.

Done-criterion met, verified live: OpenCost logs `Success: retrieved the 'up' query`,
detects AWS from `node.spec.providerID` with no CUR integration, and Grafana Cloud now
returns `opencost_build_info`, `container_cpu_allocation` (2.52 CPU) and
`node_total_hourly_cost` = **0.087** across 2 nodes — the exact `c5a.large` on-demand list
price in eu-central-1. Two caveats recorded rather than fixed: the pod restarted once at
startup because scope propagation had not reached the edge it hit (self-healed ~11s
later), and a residual ~2/min 401 on network-cost queries is logged in SESSION.md.

Research backing every prerequisite above: `docs/research/grafana-cloud-opencost-cost-metrics.md`.

2026-08-07 triage: state confirmed as `ready-for-agent`. The open token-scope question
was the one thing arguing against that label, and it is resolvable by a cheap probe
rather than by investigation — so the prerequisite section above now specifies the probe
and both branches up front, which makes the ticket self-contained either way. Maintainer
chose this over demoting to `needs-info` or splitting the token work into its own ticket.
