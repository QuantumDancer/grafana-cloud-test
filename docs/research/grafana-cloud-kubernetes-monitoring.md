# Grafana Cloud Kubernetes Monitoring — capabilities and k8s-monitoring Helm chart v4 feature blocks

- **Chart version researched:** k8s-monitoring **4.3.2** (latest GitHub release `k8s-monitoring-4.3.2` on the `main` branch of [grafana/k8s-monitoring-helm](https://github.com/grafana/k8s-monitoring-helm))
- **Docs researched:** Grafana Cloud documentation under `grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/` and related product sections
- **Access date:** 2026-08-06
- **Note on chart docs location:** the chart repo's own `docs/Features.md` and `docs/Migration.md` are now redirect stubs; the canonical chart documentation lives in the Grafana Cloud docs under [Helm chart config](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/) ([Migration.md redirect](https://raw.githubusercontent.com/grafana/k8s-monitoring-helm/main/charts/k8s-monitoring/docs/Migration.md)). Values-level facts below were verified directly against the chart source (`charts/k8s-monitoring/values.yaml` and feature sub-charts on `main`).

## Summary

Grafana Cloud Kubernetes Monitoring is a Cloud-hosted app that gives cluster → namespace → workload → node → pod → container drill-down views, automatically provisioned alerting/recording rules with runbooks, resource-efficiency analysis, ML-powered CPU/memory usage predictions, CPU outlier-pod detection, OpenCost-based cost monitoring with savings recommendations, and Kepler-based energy metrics ([overview](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/)). Data collection is done by the open-source **k8s-monitoring Helm chart v4**, which deploys Grafana Alloy collectors (via the Alloy Operator) plus optional telemetry services (kube-state-metrics, Node Exporter, Windows Exporter, OpenCost, Kepler, Beyla cache, k8s-manifest-tail) and organizes collection into independent **feature blocks** — all of which are **disabled by default** except `selfReporting` ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)). The chart is backend-agnostic (any Prometheus/Loki/OTLP/Pyroscope destination), but several consuming UIs — the Kubernetes Monitoring app itself, ML predictions/outliers, cost & savings views, Application/Frontend/Database Observability — are Grafana Cloud products with no OSS equivalent. Notable for this project: the chart has a first-class **PostgreSQL integration with a `databaseObservability` block** (feeds Grafana Cloud Database Observability), **Beyla eBPF auto-instrumentation**, and documented **EKS** support including an `eks-proxy` mode for scraping the managed control plane and an EKS Fargate example.

## 1. Kubernetes Monitoring app (Grafana Cloud UI) capabilities

All of the following are features of the Cloud-hosted app, documented under [Kubernetes Monitoring](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/):

### Navigation / views
- **Kubernetes Overview home page** "shows issues that should be triaged", with fleet-level counts of Clusters, Namespaces, Nodes, Workloads and tabs for **Alerts** and **Efficiency** ([overview](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/), [navigate](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/navigate-k8s-monitoring/)).
- Hierarchical drill-down: **Clusters → Namespaces → Nodes → Workloads → Pods → Containers**, each level with list and detail pages; cluster detail shows "the details for the Cluster along with a list of Nodes within that Cluster" ([navigate](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/navigate-k8s-monitoring/)).
- Search across any Kubernetes resource by (partial) name with autocomplete; filters by Cluster/Node/Namespace/Workload/Pod/Container ([navigate](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/navigate-k8s-monitoring/)).
- Resource utilization across nodes, load balancers, persistent volumes; network bandwidth/saturation by object; logs-and-metrics correlation via Loki ([overview](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/)).

### Alerting
- "Preconfigured alerting rules are available out of the box", provisioned automatically as part of Kubernetes Monitoring — no manual install; defaults cannot be edited directly but can be duplicated and customized, or silenced; runbook links come from the **kubernetes-mixin** project and `runbooks.prometheus-operator.dev` ([respond to alerts](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/respond-to-alerts/)).
- Recording rules and alerting rules management is documented under [manage configuration](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/manage-configuration/#alerting-rules) ([respond to alerts](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/respond-to-alerts/)).
- Custom alerts can be created directly from CPU/Memory panels in the app ([respond to alerts](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/respond-to-alerts/)).

### Resource efficiency / optimization
- Efficiency views list containers **without resource requests/limits** (top 50), **CPU/memory over-requested containers** (wasted cores / GiB), and **top wasteful namespaces** ([optimize resource usage](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/optimize-resource-usage/)).
- Scheduling adjustment recommendations (affinities/anti-affinities) and early error detection such as CPU throttling alerts are called out on the overview page ([overview](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/)).

### Machine learning: predictions and outlier detection (Cloud-only)
- "Predictions for CPU and memory usage, powered by machine learning" ([overview](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/)); the resource-usage docs describe predictive graphs for CPU and memory up to one week ahead, computed from the previous week's metrics, at cluster/namespace/workload/node/pod/container levels — requiring **Grafana Machine Learning** ([navigate/explore search results](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/navigate-k8s-monitoring/); levels-and-ML detail seen in Grafana's docs via search snippets — exact page: UNVERIFIED which single page holds the full quote; the [Monitor resource usage](https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-infrastructure/kubernetes-monitoring/optimize-resource-usage/monitor-resource-usage/) page verifiably documents outlier detection but not the Predict buttons).
- **Outlier pod detection**: on a multi-Pod workload's detail page, "If there is a Pod in the workload that is an outlier for CPU usage, it is indicated in the **outliers by CPU** field. Click the link to open Explore and discover the outlier Pod." ([Monitor resource usage](https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-infrastructure/kubernetes-monitoring/optimize-resource-usage/monitor-resource-usage/)).
- The underlying **Grafana Machine Learning** outlier detection (DBSCAN and MAD algorithms) and forecasting are documented only under Grafana Cloud docs ([outlier detection](https://grafana.com/docs/grafana-cloud/machine-learning/dynamic-alerting/outlier-detection/), [forecasts/outlier detection](https://grafana.com/docs/grafana-cloud/alerting-and-irm/machine-learning/forecasts/outlier-detection/)).

### Cost monitoring (Cloud UI; OpenCost data source)
- Two views: an **Overview tab** (costs per resource and infrastructure type, historical **and projected** costs) and a **Savings tab** (savings opportunities, cost/savings trends); includes network egress and GPU expense insights ([manage costs](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/); sub-pages: [Overview tab](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/k8s-costs/), [Savings tab](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/k8s-savings/)).
- Cost methodology: nodes/clusters have "known cost" from cloud providers; containers/pods/namespaces get **allocated** costs based on "actual usage or the requested amount"; **idle cost** = unused capacity or unrequested resources ([manage costs](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/)).
- Setup requirements: see section 5 below.

### Energy / carbon
- "Energy usage data via Kepler": when configured, Kepler (CNCF eBPF energy-monitoring project) exposes node- and pod-level energy metrics that Alloy collects; in chart v4 this is configured via `hostMetrics` energy metrics + `telemetryServices.kepler.deploy` ([overview](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/), [what's new: energy data](https://grafana.com/docs/grafana-cloud/whats-new/2024-08-06-energy-data-available-for-kubernetes/), [chart values.yaml `telemetryServices.kepler`](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)). No carbon-footprint view is documented in the Kubernetes Monitoring app docs (carbon content is blog-only) — treat carbon as **not a product feature** ([Kepler/carbon blog is not product docs](https://grafana.com/blog/going-green-how-to-monitor-your-cloud-carbon-footprint-using-kepler-prometheus-and-grafana/)).

## 2. Chart v4 feature blocks

Verified directly from [`charts/k8s-monitoring/values.yaml`](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml) (main @ 4.3.2) and the feature sub-charts under [`charts/k8s-monitoring/charts/`](https://github.com/grafana/k8s-monitoring-helm/tree/main/charts/k8s-monitoring/charts). Every feature block shares the same shape: `enabled`, `destinations` (empty = all capable destinations), `dataProcessors`, `collector`.

| Values key | Collects | Default | Required destination | Primary Cloud consumer |
|---|---|---|---|---|
| `clusterMetrics` | Kubernetes cluster metrics: kubelet, kubelet resources/probes, cAdvisor, kube-state-metrics, and (opt-in, default off) control plane: API server, kube-controller-manager, kube-scheduler, kube-proxy, kubeDNS ([feature-cluster-metrics values](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/charts/feature-cluster-metrics/values.yaml)) | off | metrics | Kubernetes Monitoring app (core) |
| `hostMetrics` | Node-level metrics: Node Exporter (Linux), Windows Exporter, energy metrics via Kepler ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml), [migration doc](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/helm-chart/migrate-helm-chart/)) | off | metrics | Kubernetes Monitoring app (node views, energy) |
| `costMetrics` | Cost allocation metrics via OpenCost ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | off | metrics | Kubernetes Monitoring app → Cost views |
| `clusterEvents` | Kubernetes Cluster events from the API server ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | off | logs | Kubernetes Monitoring app (events in troubleshooting) |
| `nodeLogs` | Kubernetes node (journal/system) logs ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | off | logs | Loki / app log views |
| `podLogsViaLoki` | Pod logs from node log files, shipped in Loki format; `onlyGatherNewLogLines: true` by default ([chart README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/README.md)) | off | logs | Loki / app log correlation |
| `podLogsViaOpenTelemetry` | Pod logs from node log files, shipped as OTLP logs ([chart README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/README.md)) | off | logs (OTLP) | Loki/OTLP backends |
| `podLogsViaKubernetesApi` | Pod logs streamed through the Kubernetes API (no node file access needed — the Fargate-compatible method) ([chart README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/README.md), [EKS Fargate example](https://github.com/grafana/k8s-monitoring-helm/tree/main/charts/k8s-monitoring/docs/examples/platforms/eks-fargate)) | off | logs | Loki |
| `podLogsObjects` | Pod logs selected via `PodLogs` custom objects ([chart README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/README.md)) | off | logs | Loki |
| `applicationObservability` | Opens receivers (**OTLP gRPC/HTTP, Jaeger, Zipkin** — no Faro receiver) for app metrics/logs/traces from instrumented apps; processors incl. batch, resource detection, filter/transform, tail-sampling-capable pipeline; connectors incl. `grafanaCloudMetrics` (host-info), span logs, span metrics ([feature-application-observability values](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/charts/feature-application-observability/values.yaml)) | off | metrics+logs+traces (OTLP) | **Application Observability** ([integration doc](https://grafana.com/docs/grafana-cloud/monitor-applications/application-observability/collector/grafana-alloy-kubernetes/)) |
| `autoInstrumentation` | Deploys **Grafana Beyla** "to automatically instrument programs running on this cluster using eBPF"; produces RED metrics + (by default) delivers traces to the applicationObservability OTLP receiver (`beyla.deliverTracesToApplicationObservability: true`) ([feature-auto-instrumentation README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/charts/feature-auto-instrumentation/README.md)) | off | metrics (+traces via App O11y) | Application Observability (zero-code) |
| `annotationAutodiscovery` | Scrapes metrics from Pods/Services carrying special annotations ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | off | metrics | Prometheus/Mimir |
| `prometheusOperatorObjects` | Scrapes targets defined by `ServiceMonitor`, `PodMonitor`, `Probe` objects; **CRDs are no longer bundled in v4 — install `prometheus-community/prometheus-operator-crds` separately** ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml), [migration doc](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/helm-chart/migrate-helm-chart/)) | off | metrics | Prometheus/Mimir |
| `profiling` | Gathers application profiles; v4 lets you independently toggle **eBPF, Java, and pprof** collection ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml), [migration doc](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/helm-chart/migrate-helm-chart/)) | off | profiles (Pyroscope) | Grafana Cloud Profiles / Pyroscope |
| `profilesReceiver` | Opens a receiver for profiles pushed by applications ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | off | profiles (Pyroscope) | Grafana Cloud Profiles / Pyroscope |
| `kubernetesManifests` | **Experimental** — collects Kubernetes resource manifests and modifications as logs; requires `telemetryServices.k8s-manifest-tail` ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | off | logs | Loki |
| `integrations` | Built-in configs for common services. Available in v4: **Grafana Alloy, cert-manager, dcgm-exporter (NVIDIA GPU), etcd, Grafana, Istio, Loki, Mimir, MySQL, PostgreSQL, Tempo** ([integrations dir](https://github.com/grafana/k8s-monitoring-helm/tree/main/charts/k8s-monitoring/charts/feature-integrations/integrations), [feature-integrations README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/charts/feature-integrations/README.md)). Multiple instances per integration supported. | none enabled | metrics (+logs for some) | Grafana Cloud integrations dashboards; Database Observability (MySQL/PostgreSQL) |
| `selfReporting` | Anonymized metric+log about chart configuration (features enabled, destination types, Alloy instances); "does not report any actual telemetry data, credentials or configuration"; sent only to your configured destinations ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)) | **on** (60s interval) | metrics | — |

### Supporting v4 structures (not feature blocks)

- **`destinations` (map, required):** named destinations of type `prometheus`, `loki`, `otlp`/`otlphttp`, `pyroscope` ([chart README](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/README.md)).
- **`collectors` (map):** Alloy instances with presets (e.g. `clustered`, `statefulset`); replaces v3's fixed `alloy-metrics`/`alloy-logs`/etc. names ([migration doc](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/helm-chart/migrate-helm-chart/)).
- **`telemetryServices` (all `deploy: false` by default):** `kepler`, `kube-state-metrics`, `opencost`, `node-exporter`, `windows-exporter`, `k8s-manifest-tail`, `beyla` (k8s metadata cache), `sdkInjector` (auto-instruments apps with the Beyla SDK via the k8s-injection-controller) — v4 requires explicit deployment declarations, "preventing silent deployments" and allowing pointers to existing instances ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml), [migration doc](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/helm-chart/migrate-helm-chart/)).
- **`dataProcessors` (map):** reusable processor chains referenced from any feature's `dataProcessors` list ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)).
- **`alloy-operator.deploy: true`:** the Alloy Operator manages Alloy instance lifecycle ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)).

### v3 → v4 breaking changes (for readers of older docs/examples)

Per the official [migration guide](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/helm-chart/migrate-helm-chart/):
1. `destinations` changed from list to **map** (keys you name) — better for Helm merges/GitOps.
2. Collectors changed from fixed names to a **customizable map with presets**.
3. `clusterMetrics` split into `clusterMetrics` + `hostMetrics` + `costMetrics`.
4. `podLogs` (with `gatherMethod`) split into `podLogsViaLoki`, `podLogsViaOpenTelemetry` (+ `podLogsViaKubernetesApi`, `podLogsObjects`).
5. Telemetry services (kube-state-metrics, Node Exporter, etc.) moved to explicit `telemetryServices.*.deploy`.
6. "The Prometheus Operator CRDs are no longer bundled with the chart."
7. Profiling toggles eBPF/Java/pprof independently.

| **Grafana Machine Learning (predictions, outliers)** | No dedicated chart feature — operates on the metrics already sent by `clusterMetrics`/`hostMetrics` | [ML outlier docs](https://grafana.com/docs/grafana-cloud/machine-learning/dynamic-alerting/outlier-detection/) |

## 4. EKS-specific considerations (documented)

- **Deployment targets:** the Helm chart is documented for Amazon EKS on EC2 and **EKS on Fargate**, alongside GKE/AKS/OpenShift/etc. ([helm chart config docs](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/helm-chart-config/); chart platform examples: [azure-aks, eks-fargate, gke-autopilot, openshift](https://github.com/grafana/k8s-monitoring-helm/tree/main/charts/k8s-monitoring/docs/examples/platforms)).
- **EKS Fargate:** DaemonSets/host access are restricted, so Node Exporter doesn't work and pod logs can't be read from node files; the official example disables Node Exporter and uses `podLogsViaKubernetesApi` with Alloy's `loki.source.kubernetes` ([EKS Fargate example](https://github.com/grafana/k8s-monitoring-helm/tree/main/charts/k8s-monitoring/docs/examples/platforms/eks-fargate)). "Missing Node Exporter metrics is likely fine … That's the responsibility of the cloud provider." (same source).
- **Managed control plane scraping:** `clusterMetrics.kubeControllerManager` and `clusterMetrics.kubeScheduler` support a discovery mode `"eks-proxy"` that scrapes the **EKS Control Plane Metrics API** served at `/apis/metrics.eks.amazonaws.com/v1/kcm/container/metrics` on the API server — the documented way to get controller-manager/scheduler metrics on EKS where the control plane pods are not directly reachable ([feature-cluster-metrics values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/charts/feature-cluster-metrics/values.yaml)). All control-plane scrapes (`apiServer`, `kubeControllerManager`, `kubeScheduler`, `kubeProxy`, `kubeDNS`) default to `false` (same source).
- **EKS add-on:** Kubernetes Monitoring is also available as a native **AWS EKS add-on** as an alternative install method ([Configure the Kubernetes Monitoring EKS Add-on](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/configuration/config-other-methods/config-aws-eks/)).

## 5. Cost monitoring / OpenCost setup requirements

1. Enable `costMetrics` and deploy OpenCost via `telemetryServices.opencost.deploy: true` (both default off) ([values.yaml](https://github.com/grafana/k8s-monitoring-helm/blob/main/charts/k8s-monitoring/values.yaml)); cost monitoring "must be configured with Grafana Kubernetes Monitoring Helm chart" ([manage costs](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/)).
2. Without further config, OpenCost uses **default public list pricing**; to refine estimates, configure the cloud provider's pricing/billing integration — **AWS: follow the OpenCost AWS documentation** (billing-data/Athena style integration); GCP requires enabling the Cloud Billing API and setting `CLOUD_PROVIDER_API_KEY`; Azure per OpenCost Azure docs ([manage costs](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/)).
3. The Cloud app then shows the Overview (historical + projected costs, egress, GPU) and Savings tabs ([Overview tab](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/k8s-costs/), [Savings tab](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/manage-costs/k8s-savings/)).

## 6. Cloud-only vs OSS

**Grafana Cloud-only (no OSS equivalent of the UI/feature):**
- **Kubernetes Monitoring app** (overview/triage UI, drill-down pages, efficiency views, auto-provisioned alert bundle): documented exclusively under Grafana Cloud docs and marketed as a Grafana Cloud product ([docs root](https://grafana.com/docs/grafana-cloud/monitor-infrastructure/kubernetes-monitoring/), [product page](https://grafana.com/products/cloud/kubernetes/)).
